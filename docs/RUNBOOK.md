# Operational Runbook & Incident Response

This runbook provides actionable remediation procedures and recovery playbooks for common operational failure scenarios across the Spotify Analytics Data Platform.

---

## 1. Quick Triage Flowchart

```
Pipeline Failure Alert
       │
       ▼
Identify Failing Layer:
├── A. Lambda Extractor Failure   ──> See Section 2: Spotify API & Ingestion
├── B. AWS Glue Job Failure       ──> See Section 3: Lake Processing & Schemas
├── C. Snowpipe Ingestion Lag     ──> See Section 4: Snowflake Ingestion
└── D. dbt Test Failure           ──> See Section 5: Data Quality Assertions
```

---

## 2. Playbook A: Lambda Ingestion & Spotify API Failures

### Symptoms
- Airflow `invoke_lambda` task fails with exit code or timeout.
- CloudWatch logs show HTTP `429 Too Many Requests` or `500 Internal Server Error`.

### Remediation Steps
1. **Inspect CloudWatch Logs**:
   ```bash
   aws logs filter-log-events \
       --log-group-name "/aws/lambda/spotify-playlist-raw-extractor" \
       --filter-pattern "ERROR"
   ```
2. **Verify Spotify Credentials**:
   - Check if Spotify Developer application credentials have expired or reached daily quota limits.
   - Test credentials locally using `scripts/validate_local_env.sh`.
3. **Handle Rate Limiting (429)**:
   - Ensure the client respects the `Retry-After` response header.
   - If Spotify is throttling requests, re-trigger the Airflow DAG with an increased execution interval or trigger after 1 hour.

## 3. Playbook B: AWS Glue / Spark Transformation Failures

### Symptoms
- Airflow `wait_for_glue` sensor times out or reports `FAILED`.
- Glue CloudWatch logs indicate `AnalysisException`, `SchemaMismatch`, or `OutOfMemoryError`.

### Remediation Steps
1. **Analyze Failed Spark Task**:
   - Navigate to AWS Glue Console -> Job Runs -> Select failed execution -> View CloudWatch error logs.
2. **Handle Schema Mismatch**:
   - If upstream Spotify API introduced unexpected types or dropped required fields:
     1. Download sample raw Bronze JSON from S3.
     2. Compare against `glue/schemas/bronze_schema.py`.
     3. Adjust schema or relax nullability constraints in a feature branch.
3. **Re-Run Partition Transformation**:
   - Re-execute the Glue job for the specific partition:
     ```bash
     aws glue start-job-run \
         --job-name spotify-silver-transformation-job \
         --arguments '{"--ingestion_date": "YYYY-MM-DD", "--run_id": "manual-recovery"}'
     ```

## 4. Playbook C: Snowpipe Ingestion Lag or Stalled Copies

### Symptoms
- AWS Glue finished successfully, but Snowflake `LANDING` tables show 0 rows for the target date.
- Downstream Airflow row count validation fails.

### Remediation Steps
1. **Check Snowpipe Status**:
   ```sql
   SELECT SYSTEM$PIPE_STATUS('SPOTIFY_ANALYTICS.LANDING.PIPE_LANDING_TRACKS');
   ```
   - Look for `executionState: RUNNING` and `pendingFileCount`.
2. **Inspect SQS & Load Errors**:
   ```sql
   SELECT * FROM TABLE(VALIDATE_PIPE_LOAD(
       PIPE_NAME => 'SPOTIFY_ANALYTICS.LANDING.PIPE_LANDING_TRACKS',
       START_TIME => DATEADD(HOUR, -2, CURRENT_TIMESTAMP())
   ));
   ```
3. **Manual Fallback COPY**:
   - If Snowpipe SQS notification failed, execute a manual load for the partition:
     ```sql
     COPY INTO SPOTIFY_ANALYTICS.LANDING.LANDING_TRACKS
     FROM @SPOTIFY_ANALYTICS.LANDING.STAGE_SILVER_PARQUET/tracks/ingestion_date=YYYY-MM-DD/
     FILE_FORMAT = (FORMAT_NAME = 'SPOTIFY_ANALYTICS.LANDING.PARQUET_FORMAT');
     ```

## 5. Playbook D: dbt Test Assertion Failure

### Symptoms
- `dbt test` or `dbt build` halts with failure in Airflow.
- Terminal output indicates `FAILURE 1` on assertions such as `not_null` or `relationships`.

### Remediation Steps
1. **Locate Failing Test Query**:
   - Inspect the compiled SQL query in `dbt/target/compiled/...` generated by dbt.
2. **Execute Query in Snowflake**:
   - Run the compiled test query to identify the offending rows.
   - Common causes:
     - Unexpected NULL in `artist_id` or `track_id` from local or deleted Spotify tracks.
     - Negative `duration_ms` or out-of-range `popularity` score.
3. **Quarantine or Filter**:
   - Update staging model logic in `dbt/models/staging/` to filter or coalesce anomalies, re-run `dbt build`.

## 6. Backfill & Replay Procedure

To reprocess or backfill historical dates:

1. Identify missing or corrupted date range: `START_DATE` to `END_DATE`.
2. Verify that raw JSON exists in `s3://<bucket>/bronze/spotify/playlist_tracks/` for those dates.
3. Trigger Airflow backfill DAG:
   ```bash
   airflow dags backfill \
       --start-date YYYY-MM-DD \
       --end-date YYYY-MM-DD \
       spotify_daily_snapshot_dag
   ```
4. Confirm in Snowflake that `fact_playlist_snapshot` reflects all backfilled dates.
