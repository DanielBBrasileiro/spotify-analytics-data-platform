# Data Model Specification

This document details the data schemas, entity relationships, dimensional designs, and historical snapshot models across all tiers of the Spotify Analytics Data Platform.

---

## 1. Architectural Modeling Tiers

The data model evolves across four distinct layers within Snowflake:

```
S3 Silver Parquet
       │
       ▼
1. LANDING Schema       (Raw 1:1 Parquet ingestion tables loaded via Snowpipe)
       │
       ▼
2. STAGING Schema       (dbt views with normalized naming, casting, and light deduplication)
       │
       ▼
3. CORE Schema          (dbt Kimball dimensional star schema: dimensions, facts, bridge)
       │
       ▼
4. MARTS Schema         (dbt aggregated analytical tables serving Power BI)
```

---

## 2. Layer 1: LANDING Schema (Snowflake)

Tables in `LANDING` map directly to the S3 Silver Parquet outputs generated by AWS Glue.

### `landing_artists`
| Column | Type | Nullable | Description |
| :--- | :--- | :--- | :--- |
| `artist_id` | VARCHAR(64) | NO | Spotify artist URI identifier |
| `artist_name` | VARCHAR(255) | NO | Display name of the artist |
| `popularity` | INTEGER | YES | Current artist popularity (0-100) |
| `genres` | VARCHAR(512) | YES | Comma-delimited list of genres |
| `ingestion_date` | DATE | NO | S3 partition date (YYYY-MM-DD) |
| `_loaded_at` | TIMESTAMP_NTZ | NO | Snowpipe load timestamp |

### `landing_albums`
| Column | Type | Nullable | Description |
| :--- | :--- | :--- | :--- |
| `album_id` | VARCHAR(64) | NO | Spotify album URI identifier |
| `album_name` | VARCHAR(255) | NO | Album title |
| `album_type` | VARCHAR(32) | YES | e.g., 'album', 'single', 'compilation' |
| `release_date` | VARCHAR(16) | YES | Source release date string (YYYY or YYYY-MM-DD) |
| `total_tracks` | INTEGER | YES | Declared track count on the album |
| `ingestion_date` | DATE | NO | S3 partition date |
| `_loaded_at` | TIMESTAMP_NTZ | NO | Snowpipe load timestamp |

### `landing_tracks`
| Column | Type | Nullable | Description |
| :--- | :--- | :--- | :--- |

## 3. Layer 2: STAGING Schema (dbt Models)

Staging models are implemented as ephemeral models or views in dbt:
- `stg_spotify_artists`: Casts types, standardizes naming, trims strings.
- `stg_spotify_albums`: Standardizes partial release dates (e.g., '1995' converted to '1995-01-01').
- `stg_spotify_tracks`: Enforces non-null assertions and filters invalid negative durations.
- `stg_spotify_playlist_snapshots`: Extracts snapshot calendar date and prepares fields for dimensional key hashing.

## 4. Layer 3: CORE Dimensional Schema (Kimball Star Schema)

```mermaid
erDiagram
    dim_track ||--o{ bridge_track_artist : "credited"
    dim_artist ||--o{ bridge_track_artist : "performs"
    dim_album ||--o{ dim_track : "parent"
    dim_track ||--o{ fact_playlist_snapshot : "member"
    dim_playlist ||--o{ fact_playlist_snapshot : "hosts"

    dim_track {
        string track_pk PK "Surrogate Hash (track_id)"
        string track_id NK "Spotify Track ID"
        string track_name
        string album_pk FK
        int duration_ms
        boolean is_explicit
        int latest_popularity
        timestamp created_at
        timestamp updated_at
    }

    dim_artist {
        string artist_pk PK "Surrogate Hash (artist_id)"
        string artist_id NK "Spotify Artist ID"
        string artist_name
        int latest_popularity
        string primary_genre
        timestamp created_at
    }

    dim_album {
        string album_pk PK "Surrogate Hash (album_id)"
        string album_id NK "Spotify Album ID"
        string album_name
        string album_type
        date release_date
        int total_tracks
    }

    dim_playlist {
        string playlist_pk PK "Surrogate Hash (playlist_id)"
        string playlist_id NK "Spotify Playlist ID"
        string playlist_name
        string owner_id
        boolean is_collaborative
    }

    bridge_track_artist {
        string bridge_pk PK "Surrogate Hash (track_pk + artist_pk)"
        string track_pk FK
        string artist_pk FK
        int artist_order
    }

    fact_playlist_snapshot {
        string snapshot_pk PK "Surrogate Hash"
        string playlist_pk FK
        string track_pk FK
        date snapshot_date
        timestamp snapshot_timestamp
        int track_position
        timestamp added_at
        string pipeline_run_id
    }
```

### Snapshot Natural Key & Surrogate Key Design
- **Natural Key**: A track can appear multiple times in a single playlist at distinct track positions. Therefore, the natural grain of a snapshot observation is:
  `playlist_id` + `track_id` + `track_position` + `snapshot_timestamp`
- **Surrogate Key (`snapshot_pk`)**: Generated via `dbt_utils.generate_surrogate_key(['playlist_id', 'track_id', 'track_position', 'snapshot_timestamp'])`.

## 5. Layer 4: MARTS Schema (Analytical Business Marts)

Power BI queries these curated analytical models exclusively.

### 1. `mart_artist_performance`
- **Granularity**: `artist_id` + `snapshot_date`
- **Metrics**: Total tracks in monitored playlists, average track popularity, distinct playlist reach, top ranked position.

### 2. `mart_playlist_trends`
- **Granularity**: `playlist_id` + `snapshot_date`
- **Metrics**: Total track count, average track duration, explicit track percentage, average popularity, new track count, churned track count.

### 3. `mart_track_popularity`
- **Granularity**: `track_id` + `snapshot_date`
- **Metrics**: Popularity movement, highest position achieved, current playlist memberships.

### 4. `mart_playlist_changes` (Churn & Retention Mart)
- **Granularity**: `playlist_id` + `track_id` + `snapshot_date`
- **Calculations**:
  - `status`: `'NEW'` (entered today), `'RETAINED'` (present yesterday & today), `'EXITED'` (present yesterday, gone today).
  - `position_delta`: Change in chart rank from previous snapshot.
  - `days_on_playlist`: Cumulative consecutive days present in playlist.
