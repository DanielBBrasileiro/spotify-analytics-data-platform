# 5–8 Minute Portfolio Demo Walkthrough

This script is designed for a screen-share or recorded walkthrough. Keep one successful Airflow
run artifact, the repository tree, and a Snowflake worksheet available before recording. Use
real run evidence when shown; do not replace missing live evidence with unit-test fixtures.

---

## 0:00–0:45 — Architecture in One Pass

Open `docs/ARCHITECTURE.md` and describe the path:

```text
source -> S3 Bronze -> Glue 5.1/Silver -> Snowpipe/Landing -> dbt -> MARTS/BI_* views
                                      ^
                                      |
                                  Airflow 3
```

Talking points:

- one S3 lake bucket with immutable/run-scoped `bronze/`, `silver/`, `artifacts/`, and
  `metadata/` prefixes;
- Glue handles source-shape normalization and Parquet curation;
- Snowflake/dbt handles analytical modeling;
- Airflow coordinates external boundaries and persists evidence rather than assuming a task's
  exit code proves downstream readiness.

---

## 0:45–1:20 — State the Data Boundary Before Showing Results

Say this early: the public demo uses CC0-licensed catalog metadata adapted from
`jeremycte/spotify-10000-songs-dataset`, while the three-day playlist evolution is generated by
this repository and marked `temporal_state=synthetic`.

Show `source_type=cc0_demo` and `temporal_state=synthetic` in a plan/report if available.
Explain that the system preserves this provenance so simulated playlist changes are never
presented as real Spotify observations.

---

## 1:20–2:30 — Show One Airflow Run as Evidence

Open the Airflow DAG or run graph and point out:

- Task SDK `@dag`, `@task`, and reschedule-mode sensors;
- retries with exponential backoff for transient work;
- no automatic retry on Glue submission because an ambiguous external submit can duplicate
  physical work;
- Airflow 3 `DeadlineAlert` referenced to `DAGRUN_QUEUED_AT`;
- the final run summary/evidence task.

Then generate or inspect the unified report for the exact run:

```bash
.venv/bin/python scripts/generate_run_report.py \
  --run-key '<successful-run-key>' \
  --json
```

Show these fields rather than scrolling through every artifact:

```text
status
source_type / temporal_state
start_date / end_date
physical_runs[].pipeline_run_id
physical_runs[].spotify_snapshot_id
physical_runs[].records_extracted
physical_runs[].glue_job_run_id
physical_runs[].landing_ready
physical_runs[].rejected_items
records_curated_by_dataset / records_loaded_by_dataset
dbt_nodes_passed
```

Explain that `spotify_snapshot_id` identifies source version while `pipeline_run_id` identifies
one physical processing attempt. For `source_type=cc0_demo`, `records_extracted` is the number
of items in the generated Bronze input and must not be described as a live Lambda extraction.

---

## 2:30–3:20 — Explain the Six-Dataset Landing Gate

Show one `landing-<pipeline_run_id>.json` or the corresponding `physical_runs[]` entry.
Name the six Silver/Landing datasets:

```text
artists
albums
tracks
track_artists
playlist_snapshots
playlist_observations
```

The gate checks exact run-scoped filenames, expected rows from Glue completion metadata, and
distinct Snowflake file-row numbers. dbt starts only after every required dataset is ready and
the bounded demo has zero rejected items.

The interview point is that “Glue succeeded” is not equivalent to “warehouse input is complete.”

---

## 3:20–4:05 — Show dbt Completion (`152/152` When Evidenced)

For the successful portfolio run that contains the current model/test graph, show the run
artifact/report where `dbt_nodes_passed` is `152` and describe it as **152/152** only when that
same run is known to have completed successfully.

Do not use `tests/unit/test_reporting_and_recovery.py` as proof; its `152` value is a fixture.
The demo proof must come from the real `dbt-summary.json`, `run_results.json`, or generated
`pipeline-run-report.json` associated with the run you are presenting.

Use the moment to explain the canonical fact grain:

```text
(playlist_id, snapshot_date, track_position)
```

Physical run IDs remain lineage, so replaying a date does not create a second logical fact key.

## 4:05–5:00 — Show the BI Serving Contract with SQL

The repository exposes four intended Snowflake serving views. If the run you are showing has
created and validated these views, execute concise queries such as:

```sql
USE ROLE SPOTIFY_ANALYST;
USE WAREHOUSE COMPUTE_WH;

SELECT *
FROM SPOTIFY_ANALYTICS.MARTS.BI_PLAYLIST_DAILY
ORDER BY snapshot_date, playlist_id
LIMIT 20;

SELECT *
FROM SPOTIFY_ANALYTICS.MARTS.BI_TRACK_CHANGES
ORDER BY snapshot_date, playlist_id, track_id
LIMIT 20;

SELECT *
FROM SPOTIFY_ANALYTICS.MARTS.BI_TRACK_DAILY
ORDER BY snapshot_date, playlist_id, track_id
LIMIT 20;

SELECT *
FROM SPOTIFY_ANALYTICS.MARTS.BI_ARTIST_DAILY
ORDER BY snapshot_date, artist_id
LIMIT 20;
```

If those views are not part of the live run being presented, show
`docs/SERVING_CONTRACT.md` and the SQL above as the consumption contract instead of claiming a
successful live query.

Call out that position displayed to BI is one-based, percentages/turnover are ratios `0–1`,
and provenance remains visible. This demonstrates a deliberate semantic handoff to any future
BI client.

## 5:00–5:50 — Demonstrate Replay Idempotency Safely

Run the recovery CLI in its default dry-run mode:

```bash
.venv/bin/python scripts/replay_partition.py \
  --date 2026-09-10 \
  --entity playlist_tracks
```

Point out `mode=dry-run` and the printed Airflow command. Explain that `--execute` would create
a new DAG run and fresh physical `pipeline_run_id` values without deleting or overwriting the
prior Bronze/Silver publications.

dbt still converges on the logical business key. That is the core idempotency story: immutable
physical attempts, stable analytical grain.

## 5:50–6:40 — Cost and IaC Controls

Open `infra/terraform/` and `docs/COST_STRATEGY.md`. Highlight controls that are visible in
code:

- one versioned S3 lake rather than multiple always-on services;
- Lambda sized for a small ingestion workload;
- Glue low-cost worker bounds and job timeout;
- seven-day CloudWatch log retention;
- least-privilege Lambda/Glue/Snowflake IAM roles;
- AWS Budget variable defaulting to `$20`/month;
- no MWAA and no NAT Gateway requirement for the portfolio architecture;
- Snowflake X-Small/auto-suspend/resource-monitor controls in the warehouse layer.

Distinguish **IaC definition** from **deployment evidence**. Terraform shows reproducible intent;
use the cost/run evidence to discuss what was actually exercised.

---

## 6:40–7:10 — Close with Explicit Non-Claims

End with the validation boundary so the demo remains credible:

- The CC0/Synthetic batch path demonstrates the data-engineering architecture and run evidence.
- Do **not** claim that the portfolio demo performed a live Spotify Lambda extraction unless a
  separate real extractor run has been captured and validated.
- Do **not** claim a Power BI dashboard or Power BI connection was validated. The repository
  currently provides a BI-ready Snowflake serving contract/views; dashboard validation is a
  separate step.
- Do not describe the synthetic three-day playlist evolution as real Spotify history.
